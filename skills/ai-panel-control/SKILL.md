# Управление Fixcat OS Manager через AI Agent API

Fixcat OS Manager — веб-панель, которая разворачивает виртуальные ОС (Ubuntu, Windows XP/7/8/10/11, Debian, Kali, Alpine) в Docker с доступом через браузер (noVNC), следит за железом и объединяет несколько ПК в «узлы». Панель предоставляет специальный API для внешнего интеллекта (нейронки): любой агент, у которого есть API-ключ панели, может читать и менять состояние панели точно так же, как пользователь через кнопки интерфейса.

## Доступ

- Базовый URL: `http://<ip-панели>:<порт>` (порт по умолчанию `3000`).
- Авторизация: заголовок `X-Fixcat-Api-Key: <ключ>`.
- Где взять ключ: раздел панели «Настройки → API для интеграции», либо `GET /api/system` (поле `apiKey`), либо `GET /api/config`. Ключ выдаётся один на панель, менять его — кнопка «Перегенерировать API-ключ» в настройках (инструмент не предусмотрен — это безопасное действие, выполняемое только человеком в интерфейсе).

API-ключ имеет права администратора: тот, у кого есть ключ, фактически управляет панелью и всеми связанными узлами. Хранить ключ как секрет, никогда не включать его в текст, логи, коммиты или переписку.

## Манифест инструментов

Полный манифест (имя, описание, параметры, права) панель сама отдаёт в `GET /api/ai/tools`:

```bash
curl -s -H "X-Fixcat-Api-Key: <ключ>" http://<ip>:<порт>/api/ai/tools
```

Каждый инструмент соответствует конкретной кнопке/пункту панели и имеет метку доступа:

- `read` — только чтение (безопасно, можно вызывать без последствий);
- `write` — изменение состояния (запуск, остановка, развёртывание, удаление, обновление).

Перед выполнением инструмента сначала получите манифест — он источник истины по параметрам.

## Вызов инструмента

```bash
curl -s -X POST -H "X-Fixcat-Api-Key: <ключ>" -H "Content-Type: application/json" \
  http://<ip>:<порт>/api/ai/run \
  -d '{"tool": "<имя>", "params": { ... }}'
```

Ответ всегда вида `{ "ok": bool, "status": <http-код>, "tool": "<имя>", "data": ... }`. `ok` — успешно ли выполнилось; `data` — результат (списки, объекты, строки). В случае ошибки параметров сервер вернёт `4xx` со списком допустимых значений.

Примеры:

- Список контейнеров: `{"tool":"list_containers","params":{}}`
- Логи контейнера: `{"tool":"container_logs","params":{"id":"<id-или-имя>"}}`
- Запуск ОС: `{"tool":"container_start","params":{"id":"<id>"}}`
- Развернуть Ubuntu 8 ГБ RAM, 4 ядра: `{"tool":"deploy_container","params":{"osType":"ubuntu","ramMb":8192,"cpuCores":4,"restartPolicy":"unless-stopped"}}`
- Автозапуск: `{"tool":"set_autostart","params":{"id":"<id>","policy":"always"}}`
- Удалённый ПК: `{"tool":"list_nodes","params":{}}`, затем `{"tool":"node_proxy","params":{"id":"<id-узла>","path":"/api/containers"}}`

## Перечень инструментов (соответствие кнопкам панели)

Контейнеры (вкладка «Контейнеры»): `list_containers`, `container_inspect`, `container_logs`, `container_start`, `container_stop`, `container_restart`, `container_remove`, `container_rename`, `deploy_container`, `list_images`.

Дашборд и мониторинг: `system_info`, `docker_info`, `stats_history`, `events`.

Связанные ПК (вкладка «Узлы»): `list_nodes`, `node_proxy`.

Автозапуск: `list_autostarts`, `set_autostart`, `autostarts_bulk`.

Оборудование (вкладка «Железо»): `hardware_cpu`, `hardware_fans`, `hardware_swap`.

Настройки: `list_users`, `config_get`, `ports_next`.

Обновление панели: `update_panel`, `restart_panel`.

## Правила поведения агента

1. Сначала читай, потом меняй. Если задача неизвестна, начни с `list_containers` + `system_info`, чтобы понять состояние хоста.
2. Определяй контейнер по `Id` или `name` из `list_containers`; имя может меняться строками, точками и цифрами — сами ID уникальны и стабильны.
3. Логи смотреть через `container_logs` (последние 150 строк). Для «почему упало» сопоставляй логи контейнера и журнал `events`.
4. Деструктивные действия (`container_remove`, `update_panel`, `restart_panel`, `autostarts_bulk`) — только после явного подтверждения пользователем. Удаление контейнера необратимо и удаляет вместе с ВМ её хранилище.
5. `update_panel` перезапускает панель; после вызова проверяй доступность через некоторое время (health-check `/api/health`).
6. Для управления удалённым ПК используй `node_proxy`: текущая панель честно проксирует только разрешённые пути (контейнеры, автозапуск, события, статистика, настройки, обновление, оборудование, образы, порты, Docker-info). Развёртывание ОС на узле делается напрямую на том ПК.
7. Перед `deploy_container` уточни логику образов: для windows-версий используется dockur (`dockurr/windows`), для Linux — accetto/webtop/kasm. Свободный порт под развёртывание подскажет `ports_next`. Для Windows GPU выделяется автоматически, если на хосте есть подходящий GPU (`gpu: true`), но это требует NVIDIA Container Toolkit на хосте.
8. Если `ok: false` — сообщи человекочитаемо, что именно не получилось, и предложи исправить параметры или проверить состояние Docker.

## Ошибки и нештатные ситуации

- `502` в ответе `run` — внутренний вызов API не удался (панель перезагружается/занята). Повтори через несколько секунд.
- `404` по инструменту — панель новее/старее манифеста; обнови панель или сверься с `GET /api/ai/tools`.
- Поле `data.truncated: true` — ответ обрезан из-за размера (подробности в `preview`).
- Если Docker-сокет недоступен, `list_containers` вернёт пустой список с `source: "docker_disconnected"` и подсказкой — это значит, что сам Docker на хосте выключен.

## Проверка связи

```bash
curl -s -H "X-Fixcat-Api-Key: <ключ>" http://<ip>:<порт>/api/health
```

Ответ `{"status":"ok","version":"..."}` означает, что панель жива и ключ принят.
